## 〇、背景：经济援助机制

主流文明每回合向受援城邦支付金币，扣款发生在 `CvPlayer::doTurnPostDiplomacy()`，通过 `GetTreasury()->ChangeGold(-iAidGold)` **直接从国库扣除**。

关键设计约束：这笔支出**有意不纳入** `calculateGoldRateTimes100()`。原因是 `DoGold()` 依据该函数结算国库，若把它折进去，会连带影响赤字科研（`GetScienceFromBudgetDeficitTimes100()`）、附庸税与所有基于金币率的 AI 启发式。代价是：所有需要"玩家真实可支配收入"的地方，都必须**自行减去**这笔支出。

本次修复的全部问题，都源于这个"需要各处自行相减"的分散设计。

## 一、第二项：C++ 与 Lua 对"可交易金率"取值不一致

### 问题

`CvPlayer::GetTradableGoldRate()` 不做截断，可返回负数；SP 侧 `TradeLogic.lua` 的同名辅助函数做了 `math.max(0, ...)`。两层对负值判定不同，导致交易界面输入框与实际交易项脱节。

**原失败路径**（毛收入 +3、援助 5 座城邦 → 可交易 = −2，续约报价中含 5 GPT）：

| 步骤 | 修复前 | 修复后 |
| --- | --- | --- |
| Lua 夹取 `min(3, −2)` → `max(0, −2)` | 0 | 0 |
| 输入框 `SetText` | 0 | 0 |
| `ChangeGoldPerTurnTrade(0)` 内 `IsPossibleToTradeItem` | `−2 < 0` → **拒绝** | `0 < 0` → **接受** |
| 交易项 `m_iData1` 实际值 | **仍是 5** | **0** |
| 结果 | 显示 0、实为 5，按"提议"送出 5 GPT | 三者一致 |

补充说明该路径的可达性：`UsGoldPerTurnAmount` 是 `UsTableGoldPerTurn` 容器内的独立 `EditBox`（见 `SimpleDiploTrade.xml`），与 `UsPocketGoldPerTurn` 按钮**不是**父子关系。口袋按钮被禁用（`iUsTradableGPT >= 1` 不成立）**不影响**该输入框可编辑——只要 GPT 项已在交易表中，输入框就处于活动状态。

### 改动

`CvGameCoreDLL_Expansion2/CvPlayer.cpp:11507`

```cpp
int CvPlayer::GetTradableGoldRate() const
{
	const int iTradable = calculateGoldRate() - GetEconomicAidExpensePerTurn();
	return std::max(0, iTradable);
}
```

用 `std::max` 而非本文件里也出现过的小写 `max` 宏——宏展开为 `((a) > (b) ? (a) : (b))`，会把 `GetEconomicAidExpensePerTurn()`（内含 41 次循环）求值两遍。先取局部变量 + `std::max` 规避。

### 回归核对（逐点确认中性）

| 调用点 | 修复前 | 修复后 | 判定 |
| --- | --- | --- | --- |
| `CvDealAI` ×2 `if (GetTradableGoldRate() > 0)` | 负值不满足 | 0 仍不满足 `> 0` | 分支不变 ✅ |
| 和平条约 `min(GetTradableGoldRate(), x)` | 负值 → `if (iGPT > 0)` 跳过 | 0 → 同样跳过 | 行为一致 ✅ |
| `TradeLogic` 口袋启用 `iUsTradableGPT >= 1` | 负值禁用 | 0 仍禁用 | 不变 ✅ |
| `AddGoldPerTurnTrade` 的 `min(goldPerTurn, tradable)` | 只在口袋启用时可达 | 同上，tradable ≥ 1 | 不会传入 0 ✅ |
| 实际扣款 | 走 `IsAidingCityState`，不经此函数 | 同 | 扣金逻辑不变 ✅ |

### 后续：floor 规则收敛到 C++ 单点

上面的修复让 C++ 与 Lua 在数值上一致了，但 **floor 逻辑仍分处两份**：C++ 一份，SP 的 `TradeLogic.lua` 与 `DiploTradesStatus.lua` 各一份重复实现（`math.max(0, player:CalculateGoldRate() - player:GetEconomicAidExpensePerTurn())`）。将来若要调整口径（比如改成只允许交易正数的一部分），漏改任意一处就会重新引入本节开头那类"显示与交易项脱节"的缺陷。

因此把 `GetTradableGoldRate()` 导出到 Lua，两处改为直接调用：

**MPDLL** — `Lua/CvLuaPlayer.cpp` 加 `Method(GetTradableGoldRate);` 与 `lGetTradableGoldRate` 实现，`Lua/CvLuaPlayer.h` 加声明。无参数，绑定写法与相邻的 `GetEconomicAidExpensePerTurn` 一致。

**SP** — `TradeLogic.lua` 的 local 函数退化为 nil 保护的薄包装，6 个调用点一行未动：

```lua
local function GetTradableGoldRate( playerID )
	local player = Players[ playerID ]
	if player == nil then
		return 0
	end
	return player:GetTradableGoldRate()
end
```

`DiploTradesStatus.lua` 只有一处，直接内联 `pPlayer:GetTradableGoldRate()`，顺带删掉局部变量 `iTradableGPT`。

至此 floor 规则只在 `CvPlayer::GetTradableGoldRate()` 一处定义，且它同时是 `CvDeal::IsPossibleToTradeItem` 的校验依据。

> 注意区分：`TradeLogic.lua:1892` 的 `math.max( 0, min( tonumber( string ) or 0, goldRate ) )` **保留不动**。它防的是**玩家在输入框里敲负数**，不是金率本身为负——`min(typed, goldRate)` 在 typed 为负时仍会返回负值，所以这层 floor 是必要的，与本次收敛无关。

## 二、第三项 1：`IsAidingCityState` 入参范围保护

`CvGameCoreDLL_Expansion2/CvPlayer.cpp:11436`

该函数是公开头文件接口，原先直接把 `eMinor` 交给 `GET_PLAYER()`。`GET_PLAYER` 在 release 版无越界保护，传 `NO_PLAYER`(−1) 会以负下标索引 `m_apPlayers` 并解引用野指针。当前两个调用点都在 `[MAX_MAJOR_CIVS, MAX_CIV_PLAYERS)` 内安全，但同文件的 `CvMinorCivAI::CanMajorWithdrawEconomicAid` 都有 guard。

在 `#if defined(MOD_SP_UNIQUE_CITYSTATE)` 内、任何 `GET_PLAYER` 之前插入：

```cpp
	// Guard the index before GET_PLAYER(): this is a public helper, and an out-of-range
	// PlayerTypes would index m_apPlayers out of bounds in release builds.
	if (eMinor < MAX_MAJOR_CIVS || eMinor >= MAX_CIV_PLAYERS)
	{
		return false;
	}
```

## 三、第三项 2：Tooltip 文案自相矛盾

`TXT_KEY_EO_EX_ECONOMIC_AID_TT` 原文声称"不计入常规金币收支计算"，但本次改动恰恰把这笔钱加进了同一面板的"总支出"——挂在支出行上的提示语否定了它所在的这一行。

新文案改为陈述机制本身，避开矛盾：

| 语言 | 修复前 | 修复后 |
| --- | --- | --- |
| en_US | `Withdrawn straight from the treasury; not part of the regular gold income and expense calculation` | `Deducted straight from the treasury, regardless of your gold rate` |
| zh_CN | `该支出直接从国库扣除，不计入常规金币收支计算` | `直接从国库扣除，不受金币率影响` |
| zh_Hant_HK | `該支出直接從國庫扣除，不計入常規金幣收支計算` | `直接從國庫扣除，不受金幣率影響` |

选"不受金币率影响"而非"不计入计算"，是因为它描述的是 `doTurnPostDiplomacy` 里 `ChangeGold(-iAidGold)` 的真实行为：金币率为负时援助照付。这是玩家真正需要知道的信息，且与事实无出入。

## 四、第三项 3：EconomicGeneralInfo 注释措辞

`UI/InGame/Popups/OverviewAddendum/EconomicGeneralInfo.lua:667`

原注释断言该行"使各支出项之和等于玩家看到的总数"——不成立。即便加了援助行，差额仍来自两处**原版遗留**：

- 单位补给费在 `CalculateInflatedCosts()` 内，却没有对应显示行
- 外交行镜像的 `GetGoldPerTurnFromDiplomacy()` 已被计入 `CalculateGrossGoldTimes100()`（已在总收入里净掉），本身不属于总支出

改为：

```lua
    -- Economic Aid: itemised out of TotalExpenseValue above so the player can see where the money
    -- goes. The expense rows still do not sum to that total, for two pre-existing reasons: unit
    -- supply is inside CalculateInflatedCosts() but has no row of its own, and the Diplo row
    -- mirrors a term that is already netted inside GrossGold rather than being a separate expense.
```

**代码未改动**——这是原版就存在的账目差异，不在本次修复范围，只修正注释中不准确的断言。
