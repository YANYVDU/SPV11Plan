## 〇、背景：任务需求

需求原文（`2.周边维护/专家槽位整合.txt`）：

> 现状：城市专家槽位直接绑定建筑class，且存在同class不同type的建筑时，会出现问题
> 问题：每个专家强制要求绑定自己上的哪一个建筑的槽位，这直接导致槽位的多样化扩展受限
> 需求：城市新增数组，直接记录该城市每种专家槽有多少个，建筑提供专家槽改为直接修改数组内容，同时原来的UI上要求专家必须绑定自己上的哪个建筑的哪个槽位这个设定直接废弃，专家部分的城市UI也废弃原有的计算方法，改成直接读取数组内容。

需求可拆为四条：

1. 城市新增一个数组，按专家类型记录该城市拥有多少个槽位；
2. 建筑提供专家槽时改为直接修改该数组（不再由 UI 端扫描建筑推导）；
3. UI 上"专家必须绑定某个建筑的某个槽位"的设定废弃；
4. 城市 UI 的专家面板废弃原有算法（遍历建筑累加），改为直接读该数组。

### 关键设计一：不新增序列化成员

槽位数组复用了 `CvCity` 中原本已注册进 `m_syncArchive`、已参与序列化、但**从未被任何代码写入**的休眠字段 `FAutoVariable<std::vector<int>, CvCity> m_paiMaxSpecialistCount`（构造见 `CvCity.cpp:383`，`reset()` 中已 `resize` 并清零，见 `CvCity.cpp:1524-1534`，读写见 `CvCity.cpp:21163` / `21627`；均属 SDK 基线提交 `6d5b853` 的既有成员）。因此**存档格式零变化，无需 `MOD_DLL_VERSION_NUMBER` 变更**，绕开了"内测期不升版本号"的约束。旧存档该字段恒为 0，由重建钩子补票。

### 关键设计二：槽位口径 = `SpecialistCount × GetNumBuilding()`

库存的语义是"这座城市拥有几格某类专家槽"，因此它必须镜像**游戏判定"城市是否拥有该建筑"的口径**，即 `CvCityBuildings::GetNumBuilding()`：

```cpp
if(GC.getCITY_MAX_NUM_BUILDINGS() <= 1)
    return std::max(GetNumRealBuilding(eIndex), GetNumFreeBuilding(eIndex));   // 缓存库实查 = 1
```

初版实现把钩子放在 `CvCity::processBuilding`，直接用 `processBuilding` 的 `iChange` 累加。但 `iChange` 只是**调用者改动的那一个计数器**的增量（`SetNumRealBuildingTimed` 传 real 增量、`SetNumFreeBuilding` 传 free 增量），当一座建筑同时存在"自建副本"与"免费副本"（`real=1, free=1`）时两处会各加一次 → 库存翻倍，而游戏只认 1 座。旧口径（原 `CvCity::HasSpecialistSlot` 扫 `HasBuilding`、旧 CityView 循环、旧 `IsCanAddSpecialistToBuilding`）都是"每建筑类型一次"。

修正方式：把钩子**下沉到建筑计数的真正变更点**（`SetNumRealBuildingTimed` / `SetNumFreeBuilding`），传入 `GetNumBuilding()` 的**前后差**。该口径同时带来一个收益：**过时建筑继续提供槽位**，与原版一致（原版 `HasSpecialistSlot` 只查 `HasBuilding`，`processBuildingObsolete` 也不改变 `GetNumBuilding`），因此重建与增量天然同口径、无需任何过时特判。

## 三、正确性核对（通过项）

以下为本轮已逐项核对并确认无问题的点，均附证据。

1. **旧存档兼容，零版本门控**：`m_paiMaxSpecialistCount` 在基线就已序列化，本次未改格式；旧档该值恒 0，由 `CvCityCitizens::Read` 末尾（`CvCityCitizens.cpp:165-173`）调 `RebuildMaxSpecialistCountsFromBuildings()` 补票。
2. **读档时序安全**：`CvCity::read` 顺序为 `reset()`（`:20891`）→ `m_pCityBuildings->Read`（`:21132`）→ `m_paiMaxSpecialistCount`（`:21163`）→ `m_pCityCitizens->Read`（`:21298`），重建时建筑数据已可用。
3. **建城时序安全**：`CvCity::CvCity` 构造 → `reset(0, ...)`（`:461`）；`CvCity::init` 在 `:499` 调 `reset`（库存清零在 `:1524`）、`:640` 才授予免费建筑，晚于清零；且 `ChangeMaxSpecialistCount` 已改为按需 `resize`，任何早于 `reset` 的写入也不会被丢弃。
4. **占领/新建城市不重复计数**：`acquireCity` → `initCity` → `CvCity::init` 走"先 `reset` 清账、再逐建筑 `SetNumRealBuildingTimed` 累加"，不会基础值 + 增量双计。
5. **多实例建筑口径一致**：`SetNumRealBuilding(eBuilding, Count > 1)` 在两处钩子中都表现为 `GetNumBuilding` 的变化量，`Δ × SpecialistCount` 正确。
6. **`HasSpecialistSlot` 语义变化无副作用**：全仓库仅 `CvCity.cpp:24016`（定义）、`CvPlayer.cpp:36325`（唯一 C++ 调用者，其自身无调用者）与 Lua 导出引用；SP/MPDLL 的 `.lua`/`.xml` 零引用。
7. **`GetNumSpecialistsInBuilding`（逐建筑）的既有消费者未受影响**：`CvCultureClasses.cpp:4124/4134/4144` 位于 `CvPlayerCulture::LogCultureData()`，是调试日志（**注意：审前曾误判为行会加成，实为日志**）；行会类伟人产出走 `ChangeBuildingGreatPeopleRateChanges`，不依赖逐建筑占用。
8. **卖出建筑路径正确**：`CvCityBuildings::DoSellBuilding`（`CvBuildingClasses.cpp:5138`）先逐专家清空镜像、再 `SetNumRealBuilding(0)` 触发库存 `−容量`，差额由 `DoEnforceSpecialistSlotLimit` 兜底。
9. **`DoEnforceSpecialistSlotLimit` 终止性**：循环条件 `count > max >= 0 ⇒ count > 0`，而 `DoRemoveSpecialistInternal` 在 `count > 0` 时必返回 true 并自减，`count` 严格下降，无死循环、无递归。
10. **`doTask` 两个分支共用末段**：`TASK_REMOVE_SPECIALIST` 的 `NO_BUILDING` 分支与建筑分支共用 `DoAddBestCitizenFromUnassigned()`（`CvCity.cpp:2813-2820`），移除专家后的市民会自动回填地块。
11. **无第三条建筑计数路径**：`git grep m_paiNumRealBuilding` / `m_paiNumFreeBuilding` 显示写入点仅 `SetNumRealBuildingTimed`（`:5376`）与 `SetNumFreeBuilding`（`:5624`），其余为 `Init` 分配、`reset` 清零、`Read` 反序列化；题目点名的全部调用点（`CvPlayer`、`CvTeam`、`CvMinorCivAI`、`CvUnit`、`CvUnitCombat`、`CvWorldBuilderMapLoader`、Lua `SetNumFreeBuilding` 等）**全部经这两个 setter**。
12. **`maxCount` 与建筑恒同步 / `count` 不会长期超额**：唯一增 `count` 的入口 `DoAddSpecialistInternal` 经 `IsCanAddSpecialist` 保证 `count < maxCount`；唯一减 `maxCount` 的入口 `ChangeMaxSpecialistCount(iChange<0)` 必调 `DoEnforceSpecialistSlotLimit`。
13. **数据面复核**（缓存库 `Civ5DebugDatabase.db` 实查）：
    - `CITY_MAX_NUM_BUILDINGS = 1`、`MAX_SPECIALISTS_FROM_BUILDING = 4`，而单个带槽建筑 `SpecialistCount` 最大为 2 → 该上限在实际数据中永不生效。
    - 带槽建筑共 66 个（W 7 / A 7 / M 7 / S 14 / Me 18 / E 13）→ **同类型多建筑是常态**，"移除时必须挑对建筑"是高频路径而非边角。
    - 带槽且会过时的建筑**仅 `BUILDING_WORKSHOP`**（`SPECIALIST_ENGINEER ×1`，`TECH_INDUSTRIALIZATION`）。
    - 9 个带 `GetFreeBuildingThisCity` 的建筑（`GREAT_LIBRARY→LIBRARY` 等）**全部指向不同建筑类** → 重入自引用场景不可达。
    - 专家类型索引 `0=SPECIALIST_CITIZEN / 1=WRITER / 2=ARTIST / 3=MUSICIAN / 4=SCIENTIST / 5=MERCHANT / 6=ENGINEER`，与 UI 的 `GetMaxSpecialistCount(1..6)` 一致。

**P18（中，本轮最重要的发现）—— 奇观授予本城免费建筑时误踢专家。**
`CvCity.cpp:7900-7901`（原顺序）为：

```cpp
m_pCityBuildings->SetNumRealBuilding(eFreeBuildingThisCity, 0);   // 先掉
m_pCityBuildings->SetNumFreeBuilding(eFreeBuildingThisCity, 1);   // 后补
```

`SetNumRealBuilding(x, 0)` 在 `CITY_MAX_NUM_BUILDINGS = 1` 下使 `GetNumBuilding()` 由 1 瞬变为 0（`max(real, free)`），触发 `ChangeMaxSpecialistCountFromBuilding(-1)` → 减槽 → `DoEnforceSpecialistSlotLimit` **立即把在座专家踢回未分配池**；紧接着的 `SetNumFreeBuilding(x, 1)` 只把槽位补回（`iChange > 0` 不触发腾退），**被踢的专家不会自动补回**。

可达性已用缓存库核实：`FreeBuildingThisCity` 直接就是槽位建筑的有 `BUILDING_GREAT_LIBRARY → LIBRARY`（作家 1 槽，且其前置就是图书馆，城市**必有实体图书馆**）、`BUILDING_GREAT_LIGHTHOUSE → LIGHTHOUSE`（工程师 1 槽）、`BUILDING_HANGING_GARDEN → GARDEN`（SP 的 GARDEN 类含 `BUILDING_HALL_OF_WORTHIES`，作家 1 槽）、`HAGIA_SOPHIA → CATHEDRAL`（艺术家 1 槽）。复现：城市已有图书馆并在槽内派 1 名作家 → 建成大图书馆，该作家被踢回未分配池且不会自动补回。旧 DLL 无此腾退（槽位当时由建筑实时推导），故这是本次改动**新引入的行为回归**。

**P19（条件性/低）—— `changeFreeBuildingCount` 归 0 分支同源掉序。** `CvPlayer.cpp:25636-25639` 同样是"先掉后补"，命中路径为 `BUILDING_CN_TOWER → BROADCAST_TOWER`（音乐家 2 槽，玩家级免费建筑）。经查缓存库 `CustomModOptions`，`BUGFIX_BUILDING_FREEBUILDING = 1` **确实开启**，故该分支可达。
