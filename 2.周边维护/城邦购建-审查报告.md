## 〇、背景：城邦自费购买建筑机制

主流文明与城邦之间的金币流动此前是单向的（赠金、任务奖励）。本机制给城邦的国库**增加一个出口**：城邦每回合自主花钱购买防御建筑与商路建筑，使城邦城市在玩家未主动经营时也能积累基础设施。

机制由**数据驱动**：MPDLL 提供空表与执行逻辑，SP 写入具体建筑清单。表为空时不产生任何行为。

### 正确性核对（逐点确认中性）

| 检查点 | 结论 |
| --- | --- |
| 数组初始化与索引安全 | `kUtility.InitializeArray(m_pbPurchaseBuildingClass, "BuildingClasses")` 与模板签名 `InitializeArray(T*&, const char*, T)` 匹配，按 BuildingClasses 行数分配并清零；`isPurchaseBuildingClass(i)` 的断言范围与循环上界 `getNumBuildingClassInfos()` 一致 |
| 空表行为 | 清单为空时 `isPurchaseBuildingClass` 恒 false，循环内全部 `continue`，对未使用该表的其他模组**零影响** |
| 存档兼容 | `CvMinorCivInfo` 是 GC 数据（每局从数据库重建），**非序列化成员**，不涉及旧档兼容，无需版本门控 |
| 联机确定性 | 全程无 `Game.Rand`，决策仅依赖同步状态（金币、建筑、科技）；城邦 AI 在各客户端确定性重放，无分叉风险 |
| 溢出/负值 | `GetPurchaseCost` 若返回 `INT_MAX`（不可购买）会被 `pTreasury->GetGold() < iCost` 挡下；`iCost <= 0` 亦有前置过滤，无溢出扣钱路径 |

| 性能 | 每城邦每回合遍历约 200 个 BuildingClass，城邦数 ≤41，量级可忽略 |

### 问题 1（中等）：注释声称的"不在建造队列中"约束未实现

`CvMinorCivAI.cpp:2965` 起的函数头注释与循环内注释均写明：

```
// The building must already be unlocked (all construction prereqs met) and must not be
// under construction in the target city (mutual exclusion with normal production).
...
// Already unlocked by our techs, all other prereqs met, and not in the build queue
```

但代码仅调用了 `pLoopCity->canConstruct(eBuilding)`。经核对 `CvCity::canConstruct`（`CvCity.cpp:3479` 起）**全函数体内没有任何生产队列检查**（无 `getProductionBuilding` / 建造队列判断，仅有资源、地块、前置建筑等检查）。

**后果**：城邦若正在建造 Walls，仍会花金币买下 Walls。不会重复获得建筑（`SetNumRealBuilding` 幂等，队列项在生产结算时被跳过），但**金币白花**——恰是注释想避免的情形。

**建议**：二选一——补 `pLoopCity->getProductionBuilding() == eBuilding` 时跳过，或删除注释中该句使注释与实现一致。

### 问题 2（轻微）：购买"优先级"语义与实现不符

SP 侧注释称清单顺序即购买优先级（防御优先、商路其次）。但 MPDLL 实现中，当 `pTreasury->GetGold() < iCost` 时是 `continue` 到下一个**更便宜**的类别，因此金币不足时会跳过昂贵的防御建筑去买便宜的商路建筑，而非"攒钱等待最高优先级"。

**建议**：若当前行为即期望，修改 SP 注释中的 "purchase priority" 措辞；若期望"攒钱"，则改为金币不足时直接 `return`。

### 问题 3（低风险）：未加 MOD 宏门控

`DoBuildingPurchase` 未包在 `#if defined(MOD_...)` 中，与 MPDLL 其他新功能的惯例不完全一致。因是纯数据驱动（表空即无行为），实际风险低，可按仓库惯例决定是否补。

## 五、回应（2026-10-11，实现方）

逐条核实上述结论并记录处理结果。原始改动规模已由 MPDLL 3 文件 +104 变为 4 文件 +111。

### 问题 1（中等：队列检查缺失）——**误报，无需处理**

报告称 `CvCity::canConstruct` "全函数体内没有任何生产队列检查"，实为漏看函数中段（该函数近 200 行，前半段密集的 `return false` 之后才是队列判断）。`CvCity.cpp:3605` 明确有：

```cpp
	if(!bTestVisible)
	{
		if(!bContinue)
		{
			if(getFirstBuildingOrder(eBuilding) != -1)
			{
				return false;
			}
		}
```

`DoBuildingPurchase` 调用 `pLoopCity->canConstruct(eBuilding)`，用默认实参 `bContinue=false, bTestVisible=false`，恰好命中该分支。`getFirstBuildingOrder` 遍历队列匹配 `ORDER_CONSTRUCT` + `iData1 == eBuilding`，即"该建筑已在建造队列中则返回 false"。所以"城邦正在建 Walls 时仍会买 Walls"不会发生，原注释与实现一致。

已在该处注释中补一句点明检查来自 `canConstruct`，避免后续复查重复误判。

### 问题 2（轻微：优先级措辞）——**属实，已修正措辞**

实现确为"金币不足时 `continue` 到下一项"。经确认这正是既定设计意图（"买不起任何建筑就结束跳过"），故保留实现，仅修正 SP 注释为：

> The list is scanned in order and the first affordable entry is bought, so the order doubles as the purchase priority (defense first, trade routes after).

### 问题 3（低风险：MOD 宏门控）——**决定不加**

`MinorCivilization_PurchaseBuildingClasses` 为空时 `isPurchaseBuildingClass()` 恒 false，循环内全部 `continue`，对未填充该表的其他使用方零影响。同类数据驱动机制 `MinorCivilization_FreeBuildingClasses` 亦未加宏门控，保持一致。

### 问题 4（SEAPORT）——**属实，且报告低估了影响范围**

报告只发现 SEAPORT 的商路收入字段被注释。核实后是更根本的问题：**原版引擎在商路任一端为城邦时，整块屏蔽建筑商路加成**。

`CvTradeClasses.cpp:2303`（`git blame` 指向 2015-11-03 根提交 `6d5b853`，MPDLL 从未改动）：

```cpp
	// minor civs should not get bonuses for others trading with them
	if (!GET_PLAYER(kTradeConnection.m_eDestOwner).isMinorCiv() && !GET_PLAYER(kTradeConnection.m_eOriginOwner).isMinorCiv())
```

三条可能的旁路均已排查，全部走不通：

- 商路基础金 `GetTradeConnectionBaseValueTimes100` 只用全局常数 `INTERNATIONAL_TRADE_BASE` + 科技差，**不依赖目的地城市产出**；
- Harbor 的 `TradeRouteSeaGoldBonus` 走 `GetTradeConnectionYourBuildingValueTimes100`，读的是**发起城市**的加成，而城邦不发商路，永远当不了发起方；
- 城邦相关的商路加成走 `GetTradeConnectionCityStateValueTimes100` → `GetCSSeaTradeGoldBonus()`，是**玩家级**机制，与城邦城市建筑无关。

即清单中 3 条商路建筑（CARAVANSARY / HARBOR / SEAPORT）对"与城邦通商的玩家"原本零贡献，报告问题 4 只是这一现象的一个特例。

**处理**：经决策，改为放宽该门控，而非移除清单条目——

```cpp
#if defined(MOD_SP_CITYSTATE_BASIC)
	// A major civilization benefits from the trade buildings of a city-state partner, while a
	// city-state itself still gains nothing from others trading with it (the original rule)
	if (!m_pPlayer->isMinorCiv() && !(GET_PLAYER(kTradeConnection.m_eDestOwner).isMinorCiv() && GET_PLAYER(kTradeConnection.m_eOriginOwner).isMinorCiv()))
#else
	// minor civs should not get bonuses for others trading with them
	if (!GET_PLAYER(kTradeConnection.m_eDestOwner).isMinorCiv() && !GET_PLAYER(kTradeConnection.m_eOriginOwner).isMinorCiv())
#endif
```

语义：计算对象为**主要文明**时放行（即使商路另一端是城邦），城邦自身仍不获益，保留原版意图。挂在 `MOD_SP_CITYSTATE_BASIC` 下（SP 的 `DLL_Options.xml` 已置 1），非该分支行为不变。

**需留意的副作用**：该改动作用面大于"城邦购建"本身。城邦城市**已有**的建筑同样生效——原版城邦本就会自建港口/商队客栈（SP 的城邦建筑禁用规则只禁奇观、文化建筑与资源建筑，不拦它们），故加载后所有"玩家↔城邦"商路都会多出城邦城市建筑提供的 `TradeRouteTargetBonus`（SP 中港口 +10、商队客栈 +6）。这是全局性平衡变化，并非只对通过新机制买来的建筑生效。
